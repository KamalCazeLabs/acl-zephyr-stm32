Module 01 • Architecture & Setup

Foundations, Toolchain & Your First Zephyr App

Learn the core architectural principles of the Zephyr RTOS, configure your cross-platform development environment using west and the Zephyr SDK, understand the STM32 Nucleo hardware architecture, and build your first multi-board dual-LED blinky with ST-Link VCP serial console output.

⏱️ Reading Time: 25 minutes
🛠️ Lab Project: samples/01_blinky_vcp
🎯 Pre-requisites: Basic C & terminal familiarity

1.1 What is Zephyr RTOS?

Zephyr is an open-source, scalable, real-time operating system (RTOS) hosted by the Linux Foundation. Unlike traditional micro-kernels that only handle task scheduling and simple IPC (such as FreeRTOS), Zephyr provides a complete, modern operating system environment for resource-constrained microcontrollers.

Key architectural pillars that set Zephyr apart:

  • Unified Hardware Abstraction: Driven by DeviceTree (DTS). Your application C code queries hardware capabilities at compile time without hardcoding GPIO pin numbers, timer registers, or vendor peripheral addresses.
  • Granular Kconfig System: Derived from the Linux kernel. Every driver, kernel feature, stack size, and optimization flag is selected via descriptive Kconfig symbols. Unused code is completely stripped by the linker.
  • Native Multi-Repo Management (west): Zephyr uses its own meta-tool called west to track dependencies (CMSIS, HAL drivers, crypto libraries, MCUboot) with exact Git commit pinning.
  • Built-in Enterprise Security: Support for memory domain protection (MPU/MMU), stack overflow canaries, crypto subsystems, and secure firmware update flows (MCUBoot).
💡 Zephyr's Philosophy: Compile-Time Verification

In traditional RTOS programming, invalid hardware references (like querying a nonexistent UART or bad pin) often fail silently at runtime or trigger HardFaults during execution. Zephyr catches these errors at compile time through DeviceTree macros. If a peripheral is disabled in your board config, referencing it will fail during compilation!

1.2 STM32 Nucleo Family Architecture

STMicroelectronics Nucleo-64 boards are ideal for mastering Zephyr. They provide an onboard ST-LINK/V2-1 or ST-LINK/V3 debugger, meaning you do not need an external JTAG probe. The ST-Link provides two critical channels over a single USB cable:

  1. SWD (Serial Wire Debug): Flashes the STM32 Flash memory and provides hardware breakpoints via GDB or OpenOCD.
  2. VCP (Virtual COM Port): Bridges the STM32 hardware USART directly to your PC as a standard serial port (e.g., /dev/tty.usbmodem* or COMx) for print output and interactive Shell commands.
🔌 Active Board: Nucleo-F401RE Pin Map

Your active selection is the Nucleo-F401RE (ARM Cortex-M4 @ 84MHz):

  • Green User LED (LD2): Connected to PA5 (DeviceTree alias: led0)
  • Blue User Button (B1): Connected to PC13 with active-low pull-up (alias: sw0)
  • ST-Link VCP Console: USART2 on PA2 (TX) and PA3 (RX) @ 115200 baud

1.3 Toolchain Setup with west and Zephyr SDK

Zephyr applications are built using a Python virtual environment, CMake, Ninja, and the official Zephyr SDK (which includes ARM GCC toolchains and OpenOCD).

Step 1: Install Host Dependencies

BASH Host Preparation (macOS / Ubuntu Linux) 
# macOS (using Homebrew)
brew install cmake ninja gperf python3 ccache qemu dtc

# Ubuntu / Debian Linux
sudo apt update
sudo apt install -y --no-install-recommends git cmake ninja-build gperf \
  ccache dfu-util device-tree-compiler wget \
  python3-dev python3-pip python3-setuptools python3-tk python3-wheel xz-utils file

Step 2: Initialize Python Virtual Environment & west

BASH Python Venv & West Workspace 
# Create and activate virtual environment
python3 -m venv ~/zephyrproject/.venv
source ~/zephyrproject/.venv/bin/activate

# Install west
pip install west

# Initialize Zephyr workspace (clones zephyr manifest)
cd ~/zephyrproject
west init
west update

# Export CMake package & install Python dependencies
west zephyr-export
pip install -r ~/zephyrproject/zephyr/scripts/requirements.txt

Step 3: Install Zephyr SDK (ARM Toolchain)

BASH Zephyr SDK Toolchain Setup 
# Install Zephyr SDK with the arm-zephyr-eabi toolchain
cd ~
wget https://github.com/zephyrproject-rtos/sdk-ng/releases/download/v0.16.8/zephyr-sdk-0.16.8_macos-aarch64.tar.xz
# (or _linux-x86_64.tar.xz on Linux)
tar xvf zephyr-sdk-0.16.8_*.tar.xz
cd zephyr-sdk-0.16.8
./setup.sh -t arm-zephyr-eabi -h -c

1.4 Hands-On Lab 1: First Blinky & VCP Telemetry Engine

Let's examine the structure of a complete, production-ready Zephyr project. The source code is provided in your workspace at samples/01_blinky_vcp/.

1.4.1 Project Architecture

A standard Zephyr application consists of:

  • CMakeLists.txt: Tells CMake where to find Zephyr and which source files to compile.
  • prj.conf: Enables kernel features and peripheral drivers via Kconfig.
  • src/main.c: Application logic using Zephyr GPIO and kernel APIs.

1.4.2 Project Configuration: prj.conf

KCONFIG samples/01_blinky_vcp/prj.conf 
# Enable GPIO driver subsystem
CONFIG_GPIO=y

# Enable standard serial console for ST-Link VCP
CONFIG_SERIAL=y
CONFIG_CONSOLE=y
CONFIG_UART_CONSOLE=y

# Enable printk formatting support
CONFIG_PRINTK=y
CONFIG_CBPRINTF_FP_SUPPORT=y

1.4.3 Application Source Code: src/main.c

C samples/01_blinky_vcp/src/main.c 
#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>
#include <zephyr/sys/printk.h>

/* 1000 msec = 1 sec blink interval */
#define SLEEP_TIME_MS   1000

/* The devicetree node identifier for the "led0" alias */
#define LED0_NODE DT_ALIAS(led0)

#if !DT_NODE_HAS_STATUS(LED0_NODE, okay)
#error "Unsupported board: led0 devicetree alias is not defined!"
#endif

/* Retrieve GPIO specification from DeviceTree at compile time */
static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED0_NODE, gpios);

int main(void)
{
    int ret;
    uint32_t count = 0;

    printk("\n=========================================\n");
    printk("  Mastering Zephyr RTOS on STM32 - Lab 1 \n");
    printk("  Board: %s\n", CONFIG_BOARD);
    printk("=========================================\n");

    /* Verify that the underlying STM32 GPIO controller is ready */
    if (!gpio_is_ready_dt(&led)) {
        printk("Error: GPIO device %s is not ready!\n", led.port->name);
        return 0;
    }

    /* Configure GPIO pin as output with initial inactive state */
    ret = gpio_pin_configure_dt(&led, GPIO_OUTPUT_INACTIVE);
    if (ret < 0) {
        printk("Error %d: Failed to configure LED pin!\n", ret);
        return 0;
    }

    printk("LED initialized successfully on port %s, pin %d\n", 
           led.port->name, led.pin);

    while (1) {
        ret = gpio_pin_toggle_dt(&led);
        if (ret < 0) {
            printk("Error toggling LED!\n");
            return 0;
        }

        count++;
        printk("[%u s] Heartbeat Ping #%u - LED Toggled\n", 
               (count * SLEEP_TIME_MS) / 1000, count);

        /* Put thread to sleep - yields CPU to idle thread / low-power mode */
        k_msleep(SLEEP_TIME_MS);
    }

    return 0;
}

1.4.4 Building & Flashing via ST-Link

Run the following commands in your terminal to compile and flash to your connected STM32 board:

BASH Build and Flash Commands 
# Change to the sample directory
cd samples/01_blinky_vcp

# Build for your selected board:
west build -b nucleo_f401re -p always

# Flash directly to STM32 via onboard ST-Link SWD
west flash

# Open serial terminal monitor (115200 baud, 8N1)
# On macOS:
minicom -D /dev/tty.usbmodem* -b 115200
# On Linux:
minicom -D /dev/ttyACM0 -b 115200
